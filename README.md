# Paper Insight

Paper Insight 是一个本地优先的论文推荐 Web 应用，用来持续同步 arXiv 最新论文，并通过配置的大模型接口对候选论文做分析、打分和总结。

当前版本：**Paper Insight 2.1**（`2.1.0`）。本版本重点完善周报 Agent Harness、可信度门禁、局部恢复和人工复核，详细变化见 [Paper Insight 2.1 Release Notes](docs/releases/PAPER_INSIGHT_2.1.md)。

默认主题聚焦“大模型/智能体 + 网络自治/网络数字孪生/系统架构”的研究方向，包括网络自治、自智网络、零接触网络、网络数字孪生、意图网络、LLM Agent、多智能体协同、Agent 工程化集成、闭环自治和面向网络的智能体系统。查询构建器默认勾选全部背景领域词，包括 `5G/6G`、无线网络、电信网络、RAN/O-RAN、核心网、边缘网、网络切片、SDN/NFV、卫星网和光网络；用户仍可按需要取消具体领域。

## Windows 本地服务常驻运行（3100 端口）

在仓库目录运行下列命令，安装当前用户登录后自动启动的后台守护任务：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\install-local-server-watchdog.ps1 -Install -Port 3100
powershell -ExecutionPolicy Bypass -File .\scripts\install-local-server-watchdog.ps1 -Status
```

访问 `http://127.0.0.1:3100`。守护任务每 10 秒检查一次后端接口，后端退出或接口失联时按 2、5、10、30 秒退避重启。启动后保留 5 秒就绪宽限期；只终止自身启动的后端进程。关闭浏览器或 Codex 不影响计划任务，退出 Windows 登录会话或关机则停止，下一次登录重新启动。后端重启后旧任务按现有规则标记中断，需要重新执行，不支持断点恢复。

本机配置、PID、最近健康时间、错误原因和轮转日志保存在 `.cache/local-server-watchdog/`。`local-server-watchdog.log` 记录启动和退出原因；`server.stdout.log` 与 `server.stderr.log` 记录服务输出，每个日志最大约 2 MiB并保留一份轮转文件。前台诊断可运行 `npm run server:watchdog -- --config .cache/local-server-watchdog/config.json`，已有守护实例时会拒绝重复启动。

卸载命令如下，仅停止并移除守护计划任务及状态文件，保留配置、日志、论文、推荐列表、周报和 Trace：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\install-local-server-watchdog.ps1 -Uninstall
```

## 当前能力

- 从 arXiv RSS 自动同步最新论文到本地论文库。
- 从本地论文库按时间范围和查询条件筛选候选论文。
- 用户确认候选论文后，应用以固定三路并发调用所选大模型；每个请求仍只分析一篇论文。
- 单篇分析失败不会取消其他并发论文；失败论文可统一重试，也可逐篇跳过后继续，已成功分析的论文不会重复调用模型。
- 通过推荐范围判断且高于推荐阈值的论文进入推荐列表，其他论文进入隐藏列表；低于阈值或主要贡献属于硬件设计的论文不会为了凑数被补进推荐。
- 支持设置“候选目标数”：若当前时间范围内的候选不足，会保持关键词不变，依次扩展到最近 14 天、30 天；范围耗尽后按实际数量展示，不会混入放宽关键词的论文。推荐列表目标和后端分析上限都最高可设为 100。
- 支持针对单个推荐列表生成“精选论文阅读清单”：使用 Paper Insight 2.1 周报执行框架，从论文原文提取证据，完成独立复评、横向校准、确定性选稿、分段写作和发布前 QA，再生成可发布 Markdown。
- 支持论文探索页，把历史生成过的论文集中浏览。
- 支持摘要翻译，翻译必须通过 LLM API。
- 支持强制使用 arXiv API 重新获取候选，并在界面中标注候选来源。

## 核心流程

1. 在左侧确认或编辑论文搜索条件。
2. 点击“生成推荐列表”。
3. 流程弹窗展示候选获取进度。
4. 候选列表出现后，界面会显示目标数量、初始时间范围命中数和实际使用的时间范围，用户确认要分析的论文。
5. 可选择“强制 arXiv API 重新获取”，绕过本地库直接查询 arXiv API。
6. 所选大模型最多同时分析 3 篇论文，每个请求只携带一篇论文；界面展示正在分析的论文、完成数、失败数、总耗时和并发上限。
7. 如果首轮阈值以上论文数量低于“最低达标数”，应用会从下一批候选开始新一轮查询和分析；一旦达到最低达标数，就停止继续分析追加候选，而不是从低分论文里补足。候选目标最多 100 篇，推荐列表目标最多 100 篇，自动补轮最多 10 轮。
8. 如果部分论文分析失败，其他并发和后续论文仍会完成；可以只重新执行失败论文，也可以跳过当前失败论文继续，不重做已经成功的论文。
9. 分析完成后生成新的推荐列表。
10. 打开某个推荐列表后，可以点击“准备生成周报”。系统使用该列表中所有未隐藏论文作为候选，再根据候选下限划分主候选和增补候选，基于原文重新评分、校准和筛选，最后生成发布版 Markdown。
11. 可以在推荐模式、探索模式和单篇分析页之间切换。

## 论文来源

候选论文只来自 arXiv。默认路径是：

```text
arXiv RSS -> 本地 arXiv 库 -> 候选筛选 -> 用户确认 -> 大模型分析
```

强制获取路径是：

```text
arXiv API -> 候选列表 -> 用户确认 -> 大模型分析
```

候选目标数是期望展示给用户确认的候选数量，不是 arXiv 的固定返回承诺。若当前范围不足，应用仅扩大时间范围（7 天到 14 天、30 天），不放宽关键词；扩展到 30 天仍不足时会明确展示实际数量。

界面会标注每篇候选论文的来源：

- `本地 arXiv 库`：来自后端 RSS 同步后的本地论文库。
- `arXiv API`：来自 `export.arxiv.org/api/query` 的直接查询。
- `arXiv API 缓存`：来自直接 API 查询后的短期缓存或异常兜底。

更完整的论文获取、RSS 同步、本地库、429 处理和大模型输入说明见 [论文获取逻辑说明](PAPER_FETCHING_README.md)。

## 后端自动同步

后端进程会自动维护 arXiv RSS 同步，不依赖系统定时器调用 HTTP 接口。

同步判断逻辑：

- 后端读取 `.cache/arxiv-papers.json` 里的 `lastSyncedAt`。
- 按 `lastSyncedAt + ARXIV_DAILY_SYNC_MS` 计算下一次同步时间。
- 如果服务停了几天，重启后发现本地库过期，会自动同步。
- 如果刚同步过，会等到真正到期再同步。
- 同步失败后会按 `ARXIV_AUTO_SYNC_RETRY_MS` 重新尝试。

默认 RSS 分类：

```text
cs.NI, cs.AI, cs.LG, cs.MA, cs.DC, cs.IT, eess.SP, eess.SY
```

## 大模型分析

论文推荐必须使用配置的大模型接口。应用不会使用本地关键词规则兜底。

默认模型为 GLM-5.3，统一使用 BigModel Coding OpenAI 兼容接口：`https://open.bigmodel.cn/api/coding/paas/v4/chat/completions`。所有 GLM-5.3 系列请求固定发送 Thinking enabled 与 `reasoning_effort=low`；新版周报 Agent 另外使用流式响应，避免长时间等待响应头，Trace 同时记录请求档位和服务端返回的输入、输出、reasoning token。前端只在当前浏览器会话保存 API Key，已有会话中的旧 Anthropic 供应商标识会一次性迁移到 Coding OpenAI，旧的默认 `glm-5.3-flash` 会一次性迁移为 `glm-5.3`，之后仍可手动切换模型；服务端不保存密钥。

推荐分析阶段的大模型输入包括论文标题、作者、分类、日期、arXiv 链接和摘要。生成发布版周报时，服务端必须抓取 arXiv HTML 原文并通过原文质量门，再从方法、系统、实验、结果、局限和结论等章节提取绑定证据。没有可用原文的论文不会降级为摘要进入发布链路，而是被排除并继续处理其他论文或增补候选。

大模型负责生成：

- 分维度评分和兴趣适配分类
- 一句话概要
- 问题、背景、方法、技术细节、贡献、实验、网络价值和局限分析
- 阅读路径和推荐理由
- 摘要翻译

研究重点分类不由大模型自报。服务端基于论文标题、摘要和技术内容确定分类，并把可读标签和判断依据写入推荐结果。

推荐范围不包括以芯片、加速器、DRAM/HBM、RTL/Verilog、EDA、电路、微架构或硬件协同设计为主要贡献的论文。即使这类论文服务于 LLM 推理、使用多智能体或包含系统框架，也不会因此被归为通用 AI 方法并进入推荐列表。硬件仅作为实验载体、主要贡献仍是可迁移的网络自治或智能体软件方法时不受此限制。

服务端负责基于四维分项重新计算推荐总分，不直接采用模型返回的总分。这样可以保证摘要初筛、周报复评和前端展示使用同一套权重与校准逻辑。

如果 LLM 调用失败、结果缺字段、超时或没有返回某篇论文的分析，服务端会返回错误。推荐分析固定使用三路并发且每个请求只包含一篇论文；单篇失败不会取消其他论文，用户可以只重试失败论文，或逐篇跳过失败论文后继续。已成功结果会保留，应用不会自动无限重试。LLM 返回 JSON 时如果在合法 JSON 后附带少量解释文本，服务端会抽取第一段完整 JSON 对象继续处理；如果 JSON 本身不完整或缺少论文结果，仍会报错。

## 评分维度

当前使用 4 个研究质量维度辅助打分：

- 研究问题价值：20%
- 方法新意：30%
- 系统价值：20%
- 证据强度：30%

网络、AI、ICT、电信或 ADN 方向匹配不混入四维质量分，避免把“题材相关”误判成“研究质量高”。兴趣适配继续用于说明论文属于网络自治/电信、通用 AI 系统、专用非目标领域还是方向不明，但不再直接调整总分。

服务端会根据论文标题、摘要和技术分析确定研究重点，并用它对研究质量分做轻度排序校准。分类包括 Agent / Harness、AI 应用与系统、网络 AI、基础模型研究、模型内部与底层优化、硬件方向和其他 AI 研究。默认提高 Agent / Harness、应用系统和网络 AI 的排序优先级；高质量基础模型论文仍可入选；量化、词元编码、模型架构、推理优化等模型内部研究默认后移；硬件主领域仍直接排除。

服务端总分计算逻辑：

```text
researchQuality = 研究问题价值 * 0.20 + 方法新意 * 0.30 + 系统价值 * 0.20 + 证据强度 * 0.30
最终推荐分 = clamp(researchQuality + researchFocusAdjustment, 0, 100)
```

研究重点校准使用以下档位：

| 研究重点 | 校准 |
| --- | --- |
| 网络 AI | `+6`。通信网络、网络自治或网络运维中的 AI 方法与系统。 |
| Agent / Harness | `+5`。Agent 系统以及工具、记忆、规划、协作、评测、可观测性、恢复和可靠性机制。 |
| AI 应用与系统 | `+4`。用 AI 解决明确任务，并提供系统或应用层验证。 |
| 基础模型研究 | `+1`。通用大模型或基础模型能力研究；高质量成果仍保留竞争力。 |
| 模型内部与底层优化 | `-4`。量化、词元编码、模型结构、训练、推理、压缩或编译等底层细节。 |
| 其他 AI 研究 | `-2`。暂未识别出上述重点。 |
| 硬件方向 | 不进入推荐范围。 |

这意味着方法新意和证据强度仍然是主要拉开差距的质量维度；研究重点只做轻度排序校准。只有业务方向匹配但方法机制、系统设计或证据支撑不足的论文，不会因为 ICT、ADN 或电信场景相关就自动进入高分区。基础模型论文不会被排除，但需要更强的研究质量才能与优先方向竞争。

硬件主领域是独立的推荐范围准入条件，不是质量扣分项：系统仍保留其研究质量分析，但将其标记为“硬件方向（不推荐）”，无论最终分数是否超过阈值都只进入隐藏列表。历史推荐记录不会被删除；缺少该范围判断的旧分析不会在新任务中直接复用，而会重新分析。

总分档位：

| 分数段 | 含义 |
| --- | --- |
| 0-49 | 基本不达标。概念模糊、贡献弱、证据不足，或只是产业/实践/流程性内容。 |
| 50-59 | 弱相关或弱贡献。有一定问题意识或应用场景，但研究设计、方法机制或证据明显不足。 |
| 60-69 | 一般候选。方向或问题有价值，但创新、系统完整性、证据至少有一项明显短板。 |
| 70-79 | 值得扫读。问题清楚，有一定研究贡献或系统价值，但还不是强论文。 |
| 80-89 | 重点关注。问题、方法、系统或证据中至少两项比较强，值得深入读。 |
| 90-100 | 少数高价值论文。问题重要，方法有实质贡献，证据扎实，结论边界清楚，值得跟踪或复现。 |

分维度评分也使用同样档位：研究问题价值看问题是否清晰、重要、可验证；方法新意看是否有可复用的新机制、建模、任务定义或评测协议；系统价值看解决框架的模块、接口、数据流、闭环机制、部署约束和可复用性；证据强度看实验、数据、基线、消融、泛化、鲁棒性和复现线索。若只能基于摘要和元数据判断，模型必须保守评分并说明限制。

推荐分低于 60 的论文必须给出“不推荐原因”，但它不是分数解释。原因不能写“总分低于 60”“某维度多少分”或模板化阅读建议，而要像评审意见一样指出这篇论文具体差在哪里：例如方法只是流程拼装、缺少可复用机制，系统接口/闭环/失败处理没说清，实验缺少数据集/基线/消融/真实场景，或摘要只能看到愿景而看不到可验证假设。

推荐分 70 及以上的论文必须给出显性的“高分信号”。一句话描述不能只是复述论文做了什么，而要说明为什么它比普通候选更值得读：核心贡献是什么，最强维度来自研究问题、方法新意、系统价值还是证据强度，以及有哪些可核验的方法、系统或证据信号。前端会在高分论文卡片和详情页展示这条高分信号。

`ICT` 只在论文主问题域确实属于通信/电信/网络基础设施时展示，例如 5G/6G、RAN/O-RAN、无线/蜂窝/移动/核心/边缘/光/卫星网络、网络切片、路由、QoS、频谱、切换、业务保障、告警关联或故障诊断。泛 AI agent、泛多智能体、泛 graph/neural network、社交网络或只出现 `network` 一词，不会自动打 `ICT` 标签，也不会被归为网络 AI。

旧推荐分析如果缺少研究重点字段，不会在新任务中直接复用，而会重新分析。历史论文数据和已经发布的周报不会因此删除。

## 推荐展示

推荐报告包含三种视图：

- 推荐论文：通过推荐范围判断且分数达到阈值的论文。
- 隐藏论文：分数低于阈值或不在当前推荐范围的论文，仍然可以打开查看，但不会计入最低达标数。
- 全部分析：本次已分析的所有论文。

单篇论文分析页用于连续阅读，会保留大模型生成的技术分析正文，不再展示摘要和维度条。

论文探索页会汇总历史推荐列表里的论文，方便跨列表浏览和搜索。

## 阅读清单

每个推荐列表都可以生成一份“精选论文阅读清单”。周报生成是独立功能，和原始推荐列表之间只传递论文子集：原列表的推荐/隐藏、旧分数、旧排序和旧评价不会被修改，也不会直接决定周报排序。

周报以当前推荐列表中的可见推荐论文为候选范围。候选不因发表时间跨周被排除；周报生成日期仍用于标题和归档。原始推荐列表、旧分数、旧排序和旧评价不会被回写。

生成阅读清单前，可以先调四个周报专用参数：

- 复评候选下限：只用于从当前推荐列表的可见推荐论文中取一组主候选，便于把摘要初筛时低于推荐线但仍有潜力的文章纳入复评。界面范围为 `0-95`，默认 `60`，按 `5` 分步进。
- 周报入选阈值：服务端抓取原文并重新给出四维分数后，只选择复评分达到该阈值的论文。界面范围为 `40-95`，默认沿用推荐阈值或 `70`，按 `5` 分步进。
- 达标篇数目标：界面范围为 `1-20`，默认 `3`。如果主候选中达到入选阈值的论文不足，服务端会继续从当前推荐列表中未隐藏的增补池抓取原文并完成 Evidence、Review 与 Calibration。该数值是候选扩展目标，不会让低于入选阈值的论文自动入选。
- 本期最多发布篇数：界面范围为 `3-20`，默认 `5`。达到入选阈值的候选足够时，系统会用软组合约束让最终 5 篇中尽量至少有 3 篇属于 Agent / Harness、AI 应用与系统或网络 AI，再按周报复评分填充剩余名额并保持最终分数顺序。初筛或周报复评任一阶段判为专用非目标领域的论文，都不会仅凭 Agent/Harness 标签获得优先或自动入选；只有周报复评重新确认其具有通用 AI 方法价值且方法新意达到 95 分时，才作为极高创新性的跨领域例外参与选稿。人工低分纳入只能覆盖分数阈值，不能覆盖领域适配或可信度门。优先方向不足时不强行凑数，也不会纳入低于阈值的论文；其余论文仍保留在原推荐列表和 Trace 中。

前端会把当前推荐列表中的可见推荐论文拆成主候选和增补候选提交给服务端。服务端为候选抓取 arXiv HTML 原文并做本地缓存，然后基于原文摘录重新评价研究问题价值、方法新意、系统价值和证据强度，得到周报专用的新总分。抓取失败或原文质量不合格的论文不会降级为摘要进入发布链路，而是被排除并继续尝试增补候选。周报复评产生的新分数、排序、发表单位线索和入选结果只用于本次周报，不回写原始推荐列表。

论文级发表单位只从 arXiv HTML 的标题页作者区、单位节点、作者脚注和正文第一节之前的前置信息提取。系统不会从正文、实验、附录、引用、致谢、产品、供应商、客户或项目关系推断作者单位，也不建立作者到单位的对应关系；当前不读取 PDF 或 TeX。单位元数据使用 `extracted`、`not_provided` 或 `parse_failed` 状态，并保留英文原名、来源文本、来源类型和置信度。

原文缓存格式为 v3，并随正文保存论文级单位元数据。v2、缺少单位元数据或超过 TTL 的缓存会被视为未命中，重新抓取 arXiv HTML 后写回 v3。

周报生成阶段包括：

```text
候选与全文门 -> 证据提取 -> 独立复评 -> 横向校准 -> 确定性选稿 -> 策划与分段写作 -> 发布前 QA -> 发布结果
```

这些阶段由 Paper Insight 2.1 的 Agent Loop 顺序执行。Agent Harness 是服务端执行与治理层，不是另一个模型：它为每个 Agent 构造最小必要上下文，限定结构化输出契约，校验论文身份、来源引用、字段和产物集合，保存阶段 artifact，并把确定性错误的路径和要求反馈给原阶段做局部修正。周报不是由一次模型调用直接生成，也不是多个 Agent 自由对话。

Evidence、Review、逐篇 Writer 和逐篇 QA 均以单篇论文为调用边界，通过有限任务池并发执行。一个请求不会混入多篇完整原文；一篇论文失败不会取消其他论文。单篇处理失败时，Harness 会保留已经通过的论文产物，并在单篇论文范围内重试；只有 Calibration 或整稿阶段的问题才重试对应阶段，不会默认重新执行整份任务。横向校准若只遗漏部分论文，服务端保留已经有效返回的校准条目，修正请求只补充缺失论文，再按原顺序合并并复验整组结果，避免整批重生成时丢失更多条目。

当前的推荐列表、论文列表和已发布周报展示结果保存在浏览器的 `localStorage`。浏览器会把当前列表中的候选论文提交给服务端执行周报任务；服务端保存任务状态、Trace、阶段产物和原文缓存，但不保存推荐列表本身。因而更换浏览器、设备或清理站点数据后，历史列表不会自动恢复。后续将把推荐列表和发布周报元数据迁移到服务端持久化，浏览器只负责展示和操作；在完成迁移前，建议不要清理站点数据。

如果没有论文满足“复评候选下限”，前端会提示先调低候选下限。达到“周报入选阈值”的论文少于目标数量时，服务端会继续处理增补候选；增补池耗尽后，有 1–2 篇达标论文就按实际数量发布，没有达标论文才拒绝发布。低于阈值的论文不会用于补足篇数。

周报正文返回后必须通过服务端发布质量门才会保存到当前推荐列表。Paper Insight 2.1 将检查结果分为确定性硬门禁和语义告警。

确定性硬门禁包括：

- YAML 的标题、描述、日期、月份、周次、分类、标签和论文数量。
- 正文一级标题、核心章节、逐篇必填小节、完整论文清单表头和固定尾注。
- 每篇入选论文是否在正文中出现，以及是否混入未入选的 arXiv 论文。
- 每篇论文是否只有一个对应的逐篇正文条目，条目中是否串入其他论文链接。
- 发布评分、高分维度和采用“中文译名（英文原名）”格式的发表单位是否与周报复评结果及受支持的单位 Evidence 一致。
- 是否有低于入选阈值的论文进入发布稿。
- 是否有未通过原文质量门、仅有摘要的论文进入发布稿。
- 每篇论文是否至少给出两条具体的局限与适用约束。
- paperId、sourceId 和 evidenceRefs 是否属于当前论文，是否存在跨论文引用或未知来源。
- 是否包含认证信息、缺少必填产物，或者发布论文集合、顺序、评分和阅读层级与服务端结果不一致。

语义告警包括精确数字的跨语言或单位表达差异、事实支持是否充分、范围限定、机构语义、文风以及内部流程术语。它们会写入 Trace 并提示管理员，但不会仅凭模型或启发式判断自动淘汰论文或拒绝整份周报。未知校验码默认按告警处理，只有明确列入可信度策略的确定性问题才能阻断。

Paper Insight 2.1 仍依次运行确定性整稿 QA、逐篇语义 QA 和整稿语义 QA，但只有确定性硬门禁进入阻断修正链路。发现可修复的确定性问题时默认执行最多三次定向修正；修正耗尽或模型/网络处理失败后，任务暂停在统一管理员队列。界面会展示具体字段、当前表述和可取得的局部原文证据，支持逐项人工复核、继续局部修正、单篇论文范围内重试、确认当前证据、从本期周报移除论文或退出任务。只有通过全部确定性硬门禁的稿件才会保存，失败任务不会覆盖浏览器中上一份有效周报。

阅读清单由多阶段 Agent 产物和服务端确定性逻辑组装为 Markdown，标题格式为：

```text
【精选论文】YY年M月第N周阅读清单：一句话观点
```

输出内容包括：

- YAML 前置元数据，包含 `title` 和 `description`，便于发布到洞察网站。
- 正文一级标题必须直接使用完整标题：`【精选论文】YY年M月第N周阅读清单：学术主题`。冒号后的主题控制在 12-32 个 Unicode 字符，优先为 14-24 个字符；使用学术描述性短语，直接说明研究领域和具体对象、方法或评估问题，不使用问句、新闻标题或为凑长度添加的抽象词。标题不得以“研究进展”“技术进展”“领域进展”等宽泛概括收尾；多主题周报至少点明两个具体研究问题或技术机制，偏离主线的单篇方向可用“兼论 + 具体研究对象”表达。
- 报告导读先说明本周收录范围。论文方向不一致时按 1-3 个真实主题分组，每组说明具体研究对象和问题，不强行归纳为一个共同结论；首次出现的不常用术语需要解释，并优先采用通行中文技术表达。
- 本周趋势判断最多保留 2 条真正由多篇论文共同支持的结论。每条使用“短标题、变化说明、适用边界”的三段式结构：标题用 6–16 个汉字说明一个具体变化；变化说明最多两句，第一句用无需论文背景也能理解的中文说明发生了什么，第二句说明为什么值得研究或工程读者关注；边界只保留一句关键限制。公开趋势不罗列方法名、模块名、基准名、指标名或实现细节，不在一句话中堆叠多个技术概念和未解释的英文缩写，只保留理解结论所必需的术语。读者态不使用 arXiv 编号代替论文名称；单篇观察不再单独占用公开版面。
- 本周必读、值得跟进、快速扫读三个层级。
- 每篇论文的发表单位使用“中文译名（英文原名）”，括号内原名必须与该论文受支持的单位 Evidence 精确对应；模型连续返回无效单位格式时，服务端保留有效评分并回退为 Evidence 原名，不能自行补写机构。逐篇正文还包括阅读价值评分、符合的评分维度、内容方法与结果、ADN 启发与阅读价值、局限与适用约束。方法框架控制在 260 字符以内，实验与结果控制在 280 字符以内，优先保留核心机制、主要结果和证据边界；完整证据留在 Agent Loop Trace 中。
- 推荐阅读顺序和完整论文清单；完整清单使用“论文、一句话介绍、阅读级别、链接”，不重复展示发表单位、阅读价值评分或符合维度，也不展示内部阈值、复评流程或方向列。
- 最后一行由服务端固定补齐发布署名、开源联系和工具/模型说明。

## API Key

API Key 可以在页面左上角齿轮设置里输入。Key 只保存在当前浏览器会话的 `sessionStorage`，不会写入项目文件。

也可以通过环境变量提供大模型接口配置：

```powershell
$env:LLM_API_KEY="your-api-key"
$env:LLM_MODEL="your-model"
$env:LLM_API_URL="https://your-llm-provider.example/api"
node server.js
```

常用环境变量：

- `LLM_API_KEY`
- `LLM_MODEL`
- `LLM_API_URL`
- `LLM_MAX_OUTPUT_TOKENS`：默认 `128000`，控制推荐列表单篇分析的最大输出 token。
- `WEEKLY_REPORT_AGENT_MAX_OUTPUT_TOKENS`：默认 `65536`、最大 `128000`，仅控制新版周报 Agent 的结构化输出预算；不影响推荐列表分析。
- `LLM_RESPONSE_MAX_CHARS`：默认 `500000`，只做超大响应保护；不会把模型返回内容截断成短文本。
- 将周报输出预算提高到接近 `128000` 时，如确需接收极长响应，应同步评估 `LLM_RESPONSE_MAX_CHARS`；超过字符保护会明确失败，不会截断后继续发布。
- `LLM_REQUEST_TIMEOUT_MS`：默认 `600000`，控制 LLM 分析请求超时时间。
- `PAPER_ORIGINAL_TEXT_CACHE_DIR`：可选，覆盖论文原文缓存目录；本地测试使用临时目录避免污染项目缓存。
- `WEEKLY_REPORT_SEMANTIC_REVIEW_MODE`：仅供旧版同步阅读清单接口兼容使用；Paper Insight 2.1 异步周报任务始终执行语义 QA，并由集中可信度策略决定阻断或告警，不读取该开关绕过确定性硬门禁。
- `WEEKLY_REPORT_SEMANTIC_REVIEW_MAX_TOKENS`：旧版同步语义评审最大输出 token，默认 `3000`。
- `WEEKLY_REPORT_SEMANTIC_REVIEW_TIMEOUT_MS`：旧版同步语义评审超时时间，默认 `180000`。
- `WEEKLY_REPORT_SEMANTIC_EVIDENCE_MAX_CHARS`：旧版同步语义评审的论文证据总预算，默认 `60000`。

```ini
Environment=NODE_ENV=production
```

```powershell
& 'D:\Program Files\Git\usr\bin\ssh.exe' -i D:\code\paper-insight\.cache\paper_insight_ed25519 -N -L 3001:127.0.0.1:3000 <user>@<server>
```

```text
http://localhost:3001
```

### 本机 SSH 隧道守护

为避免 SSH 隧道在本机断开后需要手动重连，仓库提供了守护程序。守护程序每 10 秒请求本地周报任务接口；连接异常或它创建的 SSH 子进程退出时，会按 2、5、10、30 秒退避自动重连。它只终止自身创建的 SSH 子进程，不会操作远端服务、历史数据或其他手工 SSH 进程。

Windows 上，每台机器使用自己的服务器地址、SSH 用户和私钥安装登录后常驻任务。私钥和本机配置仅保存在 `.cache/tunnel-watchdog/`，该目录不进入 Git：

```powershell
.\scripts\install-tunnel-watchdog.ps1 -Install -RepositoryPath C:\work\code\paper-insight -Host <server> -User <user> -IdentityPath C:\keys\paper_insight_ed25519
```

安装后可查看状态或移除计划任务；卸载只删除计划任务和状态文件，不删除私钥、日志、远端数据或仓库文件：

```powershell
.\scripts\install-tunnel-watchdog.ps1 -Status -RepositoryPath C:\work\code\paper-insight
.\scripts\install-tunnel-watchdog.ps1 -Uninstall -RepositoryPath C:\work\code\paper-insight
```

首次排查可在前台运行。先通过安装脚本生成 `.cache/tunnel-watchdog/config.json`，再执行：

```powershell
npm run tunnel:watchdog -- --config .cache\tunnel-watchdog\config.json
```

日志位于 `.cache/tunnel-watchdog/tunnel-watchdog.log`，状态位于 `.cache/tunnel-watchdog/state.json`。守护核心是 Node 脚本，在其他操作系统可以使用同一份本机配置前台运行；Windows 的登录后自动启动由安装脚本负责。

常用远端命令：

```bash
sudo systemctl status paper-insight
sudo systemctl restart paper-insight
sudo journalctl -u paper-insight -f
```

- 服务重启后的断点恢复：当前只支持关闭浏览器后恢复当前任务；服务进程重启仍会把运行中的任务标记为中断。
- 原文抓取增强：在 arXiv HTML 之外继续支持 PDF 或 TeX 源文件抽取。
- 分析来源标记：在单篇推荐分析结果中标明本次分析是基于“摘要和元数据”还是“论文原文”。
- 给全文缓存增加大小上限和清理策略。

## 注意事项

- API Key 不应该提交到仓库。
- 本地缓存保存在 `.cache/`，该目录不会提交到 Git。
- 强制 arXiv API 可能遇到 `429 Rate exceeded`，这是 arXiv 服务端限流，不代表应用逻辑卡死。
- 远端部署时不要把服务直接绑定到 `0.0.0.0` 暴露公网，优先使用 SSH 隧道访问。
