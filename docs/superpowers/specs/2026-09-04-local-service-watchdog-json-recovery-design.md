# 本地服务守护与模型 JSON 安全恢复设计

## 背景

本地部署的 `paper-insight` 服务由临时命令启动时，会随 Codex 执行环境结束而退出。浏览器随后只能得到 `Failed to fetch`，现有页面容易把连接失败误解为周报质量门拒绝。与此同时，逐篇稿件生成已经出现模型返回内容完整、但遗漏最外层 JSON 闭合符的情况。现有响应格式修正再次调用模型后仍可能重复遗漏闭合符，导致本可校验的稿件进入管理员决策。

本设计对应灰度问题 `GRAY-117` 和 `GRAY-118`。

## 目标

- 本地 Windows 登录后自动启动并持续守护 `paper-insight` 后端。
- 后端进程退出或接口不可达时自动恢复，并保留明确的运行状态和日志。
- 对可以确定为“仅缺少末尾闭合符”的模型 JSON 响应执行确定性补全。
- JSON 补全后仍执行原有 Schema、Evidence、范围和文风校验，不降低质量门标准。
- 所有新行为先由自动化用例覆盖，并在 Trace 中可追溯。

## 范围与非目标

范围：

- 新增本地服务守护核心、Windows 计划任务安装脚本、状态查询和卸载能力。
- 新增可复用的模型 JSON 对象解析器，并首先接入逐篇稿件生成阶段。
- 增加守护器、安装器和 JSON 恢复回归用例。
- 更新 README 和灰度问题台账。

非目标：

- 不修改推荐范围、周报选文、评分或内容质量门规则。
- 不实现任务断点恢复；后端重启后继续沿用现有任务状态处理规则。
- 不删除或迁移论文、推荐列表、周报、任务历史和 Trace。
- 不查杀端口上的任意 Node 进程，也不管理守护器未创建的进程。
- 不修复未闭合字符串、内容中途截断或任意畸形 JSON。

## 方案选择

采用“Windows 计划任务运行 Node 守护器”的方式。

与计划任务直接运行 `server.js` 相比，守护器能够发现“进程仍存在但 HTTP 接口不可用”的情况，并提供独立状态与日志。与安装第三方 Windows Service 工具相比，该方案不增加外部依赖，也不要求把凭据写入服务配置。

## 本地服务守护设计

### 配置与安装

新增仓库脚本：

- `scripts/local-server-watchdog.mjs`：守护核心。
- `scripts/install-local-server-watchdog.ps1`：安装、卸载和状态查询。

安装脚本将运行配置写入 `.cache/local-server-watchdog/config.json`，配置包括：

- 仓库绝对路径。
- Node 可执行文件绝对路径。
- 服务端口，默认 `3100`。
- 健康检查间隔，默认 `10000` 毫秒。
- 状态目录。

计划任务名固定为 `PaperInsightLocalServerWatchdog`，以当前用户身份在登录时启动，窗口隐藏，并配置为已有实例运行时不再创建第二个实例。安装完成后立即启动任务。

### 运行流程

1. 守护器验证仓库、`server.js` 和 Node 可执行文件。
2. 以仓库为工作目录启动 `node server.js`，为子进程设置 `PORT=3100`。
3. 每 10 秒请求 `http://127.0.0.1:3100/api/reading-list/jobs/active`。
4. 收到任意有效 HTTP 响应时视为后端可达，并更新最近健康时间。
5. 子进程退出或健康检查失败时，只停止守护器自己创建的子进程，随后按 2、5、10、30 秒退避重新启动。
6. 守护器收到终止信号时停止自身子进程并记录退出原因。

启动后允许一个短暂的就绪宽限期，避免服务仍在监听端口前被健康检查误判。连续恢复由同一个互斥恢复流程处理，避免进程退出事件和健康检查同时创建两个服务。

### 所有权与数据安全

守护器只保存并操作自己创建的子进程引用，不按进程名或端口查杀进程。如果端口已被其他程序占用，守护器记录可读错误并继续按退避策略检查，不终止占用端口的程序。

安装、重装和卸载均不接触 `.cache/weekly-report-jobs`、论文缓存、推荐列表、已发布周报和 Trace。卸载只移除计划任务和当前状态文件，日志保留用于排查。

### 状态与日志

`.cache/local-server-watchdog/state.json` 记录：

- 守护进程 PID。
- 后端子进程 PID。
- 守护器启动时间。
- 最近一次后端启动时间。
- 最近一次健康检查成功时间。
- 当前重启次数。
- 最近一次失败原因。

标准输出、标准错误和守护事件写入 `.cache/local-server-watchdog/` 下的日志文件，按大小轮转。日志不记录 API Key、请求正文或论文正文。

`-Status` 同时读取计划任务状态和状态文件，区分“未安装”“已安装但未运行”“正在恢复”和“运行正常”。

## 模型 JSON 安全恢复设计

### 解析顺序

新增周报内部可复用解析器。处理顺序如下：

1. 兼容现有对象、文本块和 Markdown JSON 代码块输入。
2. 提取第一个 JSON 对象起始符之后的响应内容，并先执行标准 `JSON.parse`。
3. 仅在解析失败表现为响应末尾不完整时执行字符级扫描。
4. 扫描字符串、转义字符和对象/数组括号栈。
5. 只有满足安全条件时，按括号栈逆序追加缺失的 `}` 或 `]`，再次执行 `JSON.parse`。
6. 将解析值和规范化记录交给调用方；调用方继续执行完整业务校验。

### 允许恢复的条件

必须同时满足：

- 响应中已经找到顶层 JSON 对象起始符。
- 扫描结束时不位于字符串内部，也不存在悬空转义符。
- 不存在 `}`、`]` 类型错配或多余闭合符。
- 仅有对象或数组的末尾闭合符缺失。
- 最多补充 3 个闭合符。
- 补充闭合符后能够被标准 `JSON.parse` 解析。
- 解析结果仍能通过调用阶段的完整 Schema 和内容校验。

以下情况不得恢复：

- 字符串未闭合。
- 属性名、冒号、逗号或属性值缺失。
- 内容在字符串或数值中途结束。
- 括号类型错配。
- 需要删除、替换或猜测任何已有字符。
- 补全后字段缺失或业务校验失败。

### 接入范围与 Trace

首个接入点是 `Paper Section Writer` 的初稿、局部修正和响应格式修正。解析器设计为周报模块通用组件，但本次不批量改动其他 Agent；后续若在其他阶段出现同类真实问题，可在保持相同测试和 Trace 语义的前提下接入。

发生安全补全时，Trace 增加规范化事件，至少记录：

- 阶段与论文 ID。
- 原始解析错误类别。
- 补充的闭合符及数量。
- 补全后业务校验结果。

管理员可读描述为“模型响应末尾缺少 JSON 闭合符，系统已补全并继续校验”。它是响应格式处理记录，不显示为证据质量失败，也不计为一次模型内容修正。

## 测试策略

所有实现遵循测试先行。新增用例至少覆盖：

### 本地服务守护

- 首次启动只创建一个后端子进程。
- 健康检查成功时不重复启动。
- 子进程退出时按退避时间重启。
- HTTP 健康检查失败时只停止自身子进程并重启。
- 退出事件和健康检查同时失败时仍只执行一次恢复。
- 停止守护器只终止自身子进程。
- 配置、仓库或 `server.js` 缺失时返回可读错误。
- 安装脚本包含登录触发、隐藏运行、单实例、状态查询和安全卸载。

### JSON 安全恢复

- 缺少一个最外层 `}` 时恢复成功。
- 嵌套对象或数组只缺末尾闭合符时按逆序恢复。
- 未闭合字符串和悬空转义符不恢复。
- 括号错配或多余闭合符不恢复。
- 属性值缺失时即使追加闭合符仍拒绝。
- 超过 3 个闭合符缺失时拒绝。
- 补全后 Schema 不完整时仍由原校验拒绝。
- 使用 `GRAY-118` 的脱敏真实响应结构作为回归 fixture。
- Trace 明确记录补全，不增加模型修正次数。

## 验收标准

- 计划任务安装后，即使启动命令所在的 Codex 回合结束，本地 3100 服务仍可访问。
- 手工终止守护器拥有的后端子进程后，服务可在退避周期内自动恢复。
- 状态命令能显示当前 PID、最近健康时间和最近错误，日志能解释每次重启原因。
- 安装、重启和卸载不删除任何论文、推荐列表、周报、任务或 Trace 数据。
- `GRAY-118` 类型的响应不再触发第二次模型格式修正，而是安全补全后进入原有完整校验。
- 非安全截断继续失败，并向管理员显示具体的响应格式问题。
